GOAL: Replace the custom WebFilterChainPostProcessor with a dedicated @Order(Ordered.HIGHEST_PRECEDENCE) SecurityWebFilterChain bean that matches “/cloudfoundryapplication/**” to permit all requests, disable CSRF, and apply CORS—aligning the reactive auto-configuration with the servlet approach, preserving the existing WebFilterChainProxy and any custom firewall—and update the tests by renaming the path-ignoring test to reflect “permitted” paths and adding CSRF and cross-origin request checks.  
NEED: The previous reactive Cloud Foundry security auto-configuration post-processed the WebFilterChainProxy into a fresh instance—dropping user-provided ServerWebExchangeFirewall beans and direct setFirewall customizations and defaulting to a strict firewall— which blocked valid CF actuator requests and led to inconsistent behavior compared to non-CF or servlet deployments.  
ALTERNATIVES: The team evaluated upstream Spring Security updates, reflecting on the proxy’s private firewall field (not feasible), using WebFilterChainProxy.setFilterChainDecorator (replaces the existing decorator), injecting a firewall bean via ObjectProvider (doesn’t cover direct setFirewall calls), and even delaying the fix to 4.2.0 (unacceptably late), before adopting the servlet-style solution of adding a higher-precedence SecurityWebFilterChain for CF endpoints.
